# Design note: console session-token storage

Status: proposed. Scope: Control's Muon3D console session, not Moonraker authentication or the passkey-confirmed staff proof.

## Current design

### Token acquisition and storage

Control defines `muon.cloud.token` and `muon.cloud.refresh` as the access- and refresh-token keys (`src/services/muon-cloud/api.ts:12-18`). Its storage wrapper reads and writes `localStorage`; storage errors are ignored (`src/services/muon-cloud/api.ts:111-126`). Consequently either token is readable by every script executing on that origin. A private-mode write failure does not actually provide the comment's claimed tab session: no in-memory fallback exists.

There are two sign-in paths.

* Console-hosted Control uses OAuth authorization code plus PKCE. It enables central login only when `cloudBaseUrl()` equals the page origin and that origin is HTTPS (or loopback), explicitly excluding printer pages (`src/services/muon-cloud/centralLogin.ts:56-64`). It keeps PKCE state and verifier in `sessionStorage`, then navigates to `/authorize` (`src/services/muon-cloud/centralLogin.ts:101-127`). On callback, it validates state and issuer and consumes the pending entry (`src/services/muon-cloud/centralLogin.ts:210-242`). `initCloud` exchanges the code at `/token` and writes both returned tokens to localStorage (`src/services/muon-cloud/state.ts:330-350`). A once-per-tab silent `prompt=none` check uses the console's existing HttpOnly browser cookie and performs the same exchange and writes (`src/services/muon-cloud/centralLogin.ts:140-200`). Startup runs that check beside printer initialization, then restores the account (`src/main.ts:126-142,179-187`).
* The console sign-in UI first obtains a temporary bearer with password, MFA, passkey, or sign-up, all with `refresh: false` (`src/services/account/sign-in.ts:26-49`). It posts that bearer to `/v1/handoff`, best-effort ends the temporary session, and navigates through `/handoff` into `/authorize` (`src/services/account/sign-in.ts:67-81`; `src/views/SignIn.vue:1-18`). Thus the temporary and staff-proof credentials are not stored. The eventual OAuth callback is what stores the access/refresh pair.
* Printer-served Control does not use central login: the client registration only permits the console-hosted redirect (`src/services/muon-cloud/centralLogin.ts:1-7`). Its legacy account dialog calls `/v1/auth/sign-in`; `adoptSession` stores the returned access token (`src/services/muon-cloud/state.ts:310-319,381-389`). That response has no refresh token in this path, so a LAN session normally has only `muon.cloud.token`. `cloudBaseUrl()` selects a saved console URL, configured URL, or page origin; only the two production console origins select themselves specially (`src/services/muon-cloud/api.ts:128-156`).

`POST /token` accepts the authorization code or a refresh token and returns a rotating pair (`src/services/muon-cloud/api.ts:176-202`). A 401 on a normal console request invokes one in-tab shared refresh and replaces both localStorage values; only safe reads are retried once. A missing/refused refresh clears both (`src/services/muon-cloud/api.ts:204-255`). The account client likewise retries only `GET`; staff reads may retry through `consoleRequest`, while `staffCommand` explicitly disables 401 replay. The lock is process-local: two tabs can spend the same rotating refresh token concurrently and one can invalidate the session.

At startup `initCloud` reads the access token, calls `/v1/me`, adopts the current stored value (important if a 401 refreshed it), and clears the session after a final 401 (`src/services/muon-cloud/state.ts:359-379`). Account/printer API calls all default to `storedToken()` and send it as `Authorization: Bearer` (`src/services/muon-cloud/api.ts:232-273`). The other direct readers are the account request/refresh client (`src/services/account/client.ts:86-110`), admin request/refresh client (`src/services/admin/client.ts:51-60`), account confirmation guard (`src/services/account/confirmation.ts:8-10`), account reauthentication mixin (`src/mixins/account-reauth.ts:67-81`), deletion flow (`src/components/account/AccountDelete.vue:483-484`), community flow (`src/components/account/AccountCommunity.vue:201-239`), admin page and actions (`src/views/Admin.vue:267-331`; `src/components/admin/AdminAccountActions.vue:126-127`; `src/components/admin/AdminModeration.vue:377-428`), and Library export/change guards (`src/services/library/export.ts:19-29`). These UI readers compare token identity to discard stale asynchronous work. The Library assertion cache likewise keys itself by it (`src/services/library/assertion.ts:29-56,78-82`). The refresh token is read only by `refreshSession` (`src/services/muon-cloud/api.ts:212-229`). The console access token is not sent to `models.muon3d.com`: Control asks the console for a short-lived audience-bound assertion (`src/services/muon-cloud/api.ts:284-290`), and model requests send that assertion with credentials omitted (`src/services/library/export.ts:19-34`; `src/services/library/api.ts:1-17`). No passkey-confirmed staff proof reaches the client: `Admin.vue` retains only the actor and staff-session expiry in component state. A models staff assertion exists only as a local variable for the one audit request and is never put in durable storage.

Printer switching does not switch accounts: account state intentionally lives outside Vuex so it survives printer switches (`src/services/muon-cloud/state.ts:1-6`). The selected printer is a separate `muon.cloud.active` value. Changing account therefore means signing out, clearing the one account session, then signing in again. There is no multi-account token set.

Sign-out first clears both token keys, account state, transports, and polling (`src/services/muon-cloud/state.ts:293-308`). On console-hosted Control it then POSTs a form to `/logout`, where the console ends its browser cookie/session and issued sessions (`src/services/muon-cloud/state.ts:391-408`; `src/services/muon-cloud/centralLogin.ts:274-294`). On a printer origin it instead calls bearer-authenticated `/v1/auth/sign-out`, clears locally even if that fails, and routes to the signed-out page. Console front-channel logout frames `public/auth/logout.html`; its script removes both token keys, active printer, and browser key after issuer/referrer checks (`public/auth/logout.js:1-28`). A `storage` listener makes other same-origin tabs drop in-memory state when the access key disappears (`src/services/muon-cloud/state.ts:322-328`). Different console aliases and each `.local` printer are distinct storage/cookie origins and do not receive one another's storage events.

Offline, durable tokens survive reload, but account restoration requires `/v1/me`; a network error leaves the saved token in place without adopting an account (`src/services/muon-cloud/state.ts:364-378`). Existing local printer behavior remains available. Token-backed account, cloud-printer, and Library work requires the console and cannot truly work offline.

## Options

### A. All session authority in HttpOnly cookies; console BFF

The browser would call same-origin Control/BFF routes with an HttpOnly, Secure cookie; the BFF would call console and model services. No console bearer would be exposed to JavaScript, and proxying Library calls would avoid cross-origin credentials. This gives the strongest XSS resistance for hosted Control and makes rotation/multiple tabs server concerns.

Every state-changing BFF route would need CSRF protection (SameSite=Lax/Strict, Origin checks, and a per-session CSRF token for defense in depth); cookies are ambient authority, unlike today's explicit bearer. CSP still matters because XSS could act as the user even if it could not steal the session. The BFF must stream large model transfers and printer handoffs, expanding console load and trust.

This does not directly work for printer-served Control. A host-only `*.muon3d.com` cookie is neither a `.local` cookie nor reliably available as a third-party cookie; `SameSite=None` plus credentialed CORS would add CSRF risk and is blocked by common privacy controls. Supporting LAN pages requires a printer-side BFF/session, moving console UI to the hosted origin, or a first-party navigation bridge. It is therefore a large architectural split and poor compatibility fit.

### B. Memory-only access token; refresh token in a console HttpOnly cookie

JavaScript can use and an XSS can steal only the roughly 15-minute access token, not the long-lived refresh credential. The console rotates the Secure, HttpOnly cookie; same-origin hosted Control calls `/token` with credentials, receives an access token, and keeps it in module memory. Tabs refresh independently without racing on one JavaScript-visible rotating token. Reload and new tabs bootstrap from the cookie. CSRF protections remain required on refresh/logout and every cookie-authorized operation; refresh should require POST, validate Origin, and only return a bearer to the same origin. SameSite=Lax is suitable for hosted same-site requests and top-level OAuth navigation.

LAN pages cannot depend on third-party cookies. They need a top-level, first-party console authorization bridge that returns a single-use, PKCE-bound code to the initiating printer origin, after which the LAN page holds only an access token in memory. Reload repeats the online bridge; it must never expose a credentialed CORS refresh endpoint to arbitrary `.local` origins. Exact return-origin allowlisting/attestation and opener/message validation are essential because wildcard LAN redirects are dangerous. Until that bridge ships, the legacy LAN token path must remain during compatibility.

Cross-origin model calls remain as today: mint and send the audience-bound assertion, never the cookie or console access token. A strict CSP reduces exploitability but does not make a JavaScript-visible access token secret. Hosted multi-tab behavior improves; tabs may optionally broadcast sign-out/account-change notifications without broadcasting tokens. Offline reload loses cloud account state because memory is empty and refresh/bridge needs the network, which matches the fact that cloud operations already need the network; local printer pages must still start without waiting for it. The native phone app is a separate OAuth client and retains its refresh token in platform secure storage; browser cookie changes must not alter that grant or API contract.

### C. Keep both tokens in localStorage; strict CSP and shorter lifetimes

This is the smallest change and preserves reload, LAN, multiple-tab observation, and the current limited offline restoration behavior. A nonce/hash CSP, no unsafe script, Trusted Types where supported, dependency discipline, and short access lifetime reduce exposure.

They do not remove the core risk: any successful same-origin script execution, compromised dependency, extension with page access, or injection can read and exfiltrate the long-lived refresh token. Shortening refresh lifetime harms LAN/offline usability without preventing immediate theft. Rotation remains racy across tabs, CSP deployment differs between the Rust console and printer web servers, and CSP cannot protect against an allowed script becoming malicious. This is hardening, not a storage boundary.

## Recommendation

Choose B. It removes the durable bearer from JavaScript without forcing all Control and model traffic through a BFF, preserves the existing assertion boundary for `models.muon3d.com`, and gives a deliberate path for LAN Control. Accept that cloud account restoration after a reload is online-only. Do not use `SameSite=None` credentialed refresh from `.local` pages.

### Ordered migration and compatibility window

1. Console: add a version/capability response advertising cookie refresh and LAN authorization bridge support. Keep accepting current authorization-code and body refresh grants during the compatibility window.
2. Console: on the hosted Control authorization-code exchange, set a host-only `Secure; HttpOnly; SameSite=Lax; Path=/` rotating refresh cookie and return the access token but no refresh token when the client opts in. Bind it to client/session; reject cross-origin refresh with Origin and Fetch Metadata checks.
3. Console: add same-origin POST refresh and logout/revoke behavior, including deterministic replay handling and CSRF defenses. `/logout` must expire the cookie and retain front-channel logout for old tabs/surfaces.
4. Control: introduce an in-memory session owner. Make API/account/admin clients request an access token from it, serialize refresh there, and replace token-string identity guards/caches with a monotonically changing session identifier. Never copy a cookie or token through `BroadcastChannel`; broadcast only session-invalidated/account-changed events.
5. Control: opt in only on a capable console origin. Bootstrap with credentialed same-origin refresh, stop writing `muon.cloud.refresh`, and remove any stale refresh key after successful cookie bootstrap. Keep reading/writing the legacy pair when capability is absent.
6. Console and Control: implement the first-party LAN bridge using top-level navigation, PKCE, a short-lived single-use code, and an exact validated return origin. LAN Control keeps the resulting access token only in memory and repeats the bridge after reload/expiry. Startup must time out independently so an offline printer UI still mounts.
7. Control: keep model traffic assertion-based and credential-free. Update sign-out to clear memory first, revoke via the appropriate hosted-cookie or LAN bearer route, and retain old front-channel key clearing during compatibility.
8. Phone app: regression-test but do not migrate it; it continues using its own client and OS secure storage.
9. Compatibility window: deploy console support first, then at least one full supported Control/printer release cycle (recommended 90 days) in dual mode. Measure capability uptake, legacy `/token` refresh use, LAN bridge failures, cookie blocking, and logout propagation. Roll back by disabling client opt-in, not by reissuing exposed refresh tokens.
10. After the window, stop issuing browser refresh tokens in JSON, reject the legacy body refresh grant for client `fluidd`, delete legacy localStorage values on sight, and later remove front-channel token-key cleanup once all supported builds are past it. Keep CSP hardening in every mode.

The baseline unit test records today's two localStorage keys and their removal on sign-out (`src/services/muon-cloud/__tests__/session-restore.spec.ts`). It should change only when step 5 lands.
